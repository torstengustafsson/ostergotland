# AGENTS.md

Godot 4.7.1 (GDScript) 3D terrain demo of Östergötland, Sweden (Kimstad area), driven by a Copernicus DEM and an OSM extract. **No tests, no CI, no linter or formatter, but the scripts are kept free of GDScript warnings** — every warning is a defect to fix, not to silence with `@warning_ignore`. The source carries thorough `##` module docs on every file in `scripts/`; read those first rather than expecting this file to repeat them.

## Commands

- Engine: `/home/torsten/godot/Godot_v4.7.1-stable_linux.x86_64` (also in `.vscode/settings.json`). A 4.6 build sits beside it — do **not** use it, it would rewrite 4.7 features in `project.godot` and the `.import` files.
- Run: `<binary> --path .`, or open `main.tscn`. Physics is Jolt.
- **Verify with a smoke run** — there is nothing else:
  `timeout 30 <binary> --headless --quit-after 3`
  It boots `main.tscn` and prints load time, the heightmap extent/cell size, tile count, and the resolved spawn. The `ObjectDB instances were leaked` / `N resources still in use at exit` errors at shutdown are pre-existing and harmless.
- **No command gets a `timeout` above 30 seconds.** Never run any command with greater than 30 seconds timeout. Nearly every check here finishes in seconds, so a ceiling that generous already catches a hang. If something genuinely cannot finish inside it, split the work into shorter steps or say plainly that it needs longer — do not quietly raise the ceiling, because a run that sits for minutes is exactly how a hang goes unnoticed.
- Keep verification runs wrapped in `timeout 30`. A smoke run is ~1.5 s, so a timeout means a hang and is a bug to diagnose, not a number to raise. The usual cause is awaiting a one-shot signal that already fired — `await RenderingServer.frame_post_draw` blocks forever if the frame was presented; capture the viewport from a later `_process` instead.
- **Warnings are checked through the LSP**, because nothing else reports them (see Gotchas): `<binary> --headless --editor --path . --lsp-port 6017`, connect to `127.0.0.1:6017` with LSP framing (`Content-Length` headers), send `initialize` (rootUri `file://` + the project dir, and **`capabilities.textDocument.publishDiagnostics` has to be advertised in it** — the server never publishes a single diagnostic without it, which reads as a clean run) and wait for the reply before `initialized`, then one `textDocument/didOpen` per `.gd` file (`languageId: "godot"` plus its text) and collect `textDocument/publishDiagnostics`, whose `message` names the warning (`SHADOWED_VARIABLE_BASE_CLASS`, `INTEGER_DIVISION`, …). Two messages often arrive in one TCP read, so the reader has to keep its buffer across messages or the reply to `initialize` is silently thrown away. Wait until every file has reported once — base-class and cross-file warnings only appear after the project is indexed — then keep reading for a few seconds more. Exit code says nothing; the run is clean at **0 diagnostics**. A working check script lives in `/tmp/opencode/lsp_check.py`.
- `<binary> --headless --import` regenerates `.uid`/`.import` files after adding, renaming or duplicating scripts or assets — no need to open the editor. `.gd.uid` and `.import` files are committed; do not delete them.
- `opencode.json` denies `git *` and `opencode.json` itself: don't try to run git commands.
- `python3 assets/mapdata/osm_to_json.py` regenerates `ways.json` from `ways.osm` (stdlib only). `ways.osm` is 55 MB and takes ~23 minutes, so treat it as a deliberate, occasional act. It also accepts file names or `--all` to convert every `.osm` in the folder.

## Code style

- **Comments earn their place only by saying something the code does not**: why a sign is flipped, which order two calls must run in, what bounds a number, what breaks silently if it changes. One to three lines per block, or none. No narrating the next line, no `##` on self-explanatory accessors, no post-mortems of bugs already fixed — a comment that only matters because of a decision made elsewhere belongs in that other file.
- Keep it for the things with no other source of truth: the sign and row-order conventions, the "whole ring or nothing" rule, the reach gates, and the uniform-array sizes that must be kept in step by hand.
- **Every text file ends with a newline.** `.editorconfig` sets `insert_final_newline`; binary assets (`.exr`, `.mp3`, `.png`, `.jpg`) are the only exception.
- GDScript uses tabs; the asset-pipeline Python uses 4 spaces.

## Invariants that fail silently

These break without an error message and with the world still looking plausible. They are documented at the relevant code, and listed here so you know they exist.

**Coordinates** — the full rationale is in `osm_projection.gd` and `osm_bounds.gd`.
- **+X is east, +Z is south.** Row 0 of the DEM is its northern edge and sits at the *lowest* world Z. Putting north at +Z mirrors the whole world; every coordinate stays correct and terrain and OSM features still mirror *together*, so nothing catches it but where the player ends up facing.
- `assets/heightmap/coordinates_bounds` is the terrain's extent — `heightmap.gd` reads it, `main.gd` passes `$Heightmap.bounds` to the projection. `ways.json`'s own `bounds` is a different box (~270 m off in latitude) and must not be used for anything that lines up with terrain.
- `OsmBounds.to_pixel()` rounds to int and clamps; `OsmProjection` keeps floats and does not clamp. Ways continue past the heightmap, so the quadtree's `world_bounds()` is bigger than the terrain.

**World scale** — one world unit is one metre on all three axes.
- Horizontal scale comes from `OsmBounds.cell_size_m()` (16.145 × 30.949 m here — a degree of longitude is cos(latitude) times a degree of latitude, so the cell is *not* square). `scale` and `cell_size` are zero until `Heightmap._ready()` has run.
- The EXR holds **millimetres**. `HEIGHT_NORMALIZATION` (1000) is applied in `Heightmap._height()` and nowhere else. Skipping it puts the mesh tens of thousands of metres above its collider, so physics, forests and the player all look right while the terrain is invisible from every direction.
- The DEM is loaded as an **imported resource**, not `Image.load_from_file()`, so it survives an export — which makes the import options part of the terrain's accuracy. `output_hh.exr.import` must stay lossless (`compress/hdr_compression=0`, `detect_3d/compress_to=0`); the defaults say "VRAM Compressed" (BPTC), which quantizes millimetre values by enough to show as banding and steps in the terrain. Compare the loaded image against `Image.load_from_file()`'s `get_data()` before trusting a change here.

**Terrain tiles**
- A tile's mesh spans `TILE_SIZE + 1` columns so neighbours share edge vertices; its collision shape is one cell wider again so shapes overlap. Both must be right or seams appear — as holes in the render, as cracks in the physics.
- Normals come from the analytic height-field gradient, **not** `SurfaceTool.generate_normals()`, which would light shared edges differently and draw the tile grid onto the landscape.
- Triangles are wound **clockwise seen from above**. The reverse renders fully culled, invisible terrain whose collision still works.
- `update_stream()` measures in **world metres**, not source pixels, and `_tile_world_rect()` has to subtract `_grid_origin_offset()` or the disc is measured from the grid's own corner.

**Ground shader / OSM features**
- `OsmGroundData.MAX_LINES` (1408) and `MAX_AREA_EDGES` (576) **must** match the four `uniform vec4 ...[n]` declarations in `ground.gdshader` by hand. A uniform array's size has to be a literal in the shader (godotengine/godot#72087), which is the only reason this is manual, and a half-done resize draws the old number's worth of features with no error anywhere. The two together are the whole uniform buffer: 32 bytes an entry against a 65536-byte `LIMIT_MAX_UNIFORM_BUFFER_SIZE` (measure it — `rd.limit_get(RenderingDevice.LIMIT_MAX_UNIFORM_BUFFER_SIZE)`), so they have to stay under **2048 entries combined** and there is no room for a third array. The scans themselves — the four cover kinds, the forest floor that reuses them, and the three road surfaces — are samplers rather than array entries and do not count against this at all. Neither is slack — the line layer already drops the far half of the road network — so raising one cap costs the other.
- **A filled ring is uploaded whole or not at all.** The shader's even-odd crossing test inverts everywhere a missing side used to close the ring, so a half ring floods to infinity instead of being a smaller mistake. The area layer holds water, the four textured ground cover kinds (`landuse=farmland|meadow|grass`, `natural=beach`) and the forest floor (`landuse=forest`, `natural=wood`) — **buildings are not there**, they are geometry now (see `scripts/buildinggenerator/`), and a filled ring is flat paint, so anything that should stand up cannot use it.
- **The four cover kinds are consecutive and their order is the shader's channel order.** `area_masks()` keeps one parity and one nearest-edge distance *per kind* in the components of a `vec4` and reaches its channel by counting down from `AREA_FARMLAND`. Reordering `AREA_FARMLAND`/`MEADOW`/`GRASS`/`BEACH` in `ground.gdshader` without reordering `OsmGroundData.COVER` and `area_masks()` paints each polygon with its neighbour's texture.
- **`AREA_FOREST` is deliberately outside that run** and comes back through a separate `out` parameter. It is the one kind with no texture of its own — it blends the other three by noise — so it has no fifth channel to occupy, and the `vec4` count above stays honest. Putting it inside the run would make the channel-order invariant cover a kind that is not addressed by it.
- **The forest floor reuses the farmland/meadow/grass samplers**, not new ones: it is literally a blend of those same three scans, at their own `cover_tile_m` scales and their own `cover_tint` values, so the patches arrive level with each other. `forest_tint` on top is only the shading under a canopy. A second set of samplers would be a second copy of the same three textures.
- **The three road scans are one list, kept in step by hand in three places**, in this order: gravel (`Ground062S`), small asphalt (`Asphalt023S`), large asphalt (`Asphalt025C`). That order is the `ROAD_LOOK_*` constants in `ground.gdshader`, the `LOOK_*` constants and `ROAD_LOOKS` in `OsmGroundData`, **and** the component order of `road_tile_m`/`road_tint` — so reordering any one of the three paints each road with its neighbour's texture. The look and the class rank travel in a single float (`line_attrs.z`, see `RANK_LOOK_PACK`) because the array has no fifth component, and it is unpacked per entry in `line_masks` rather than accumulated packed, because the rank is summed weighted by coverage and a packed sum could not be split apart afterwards. Unlike the cover kinds there is **no fallback row**: a key `OsmRoad.surface_look()` returns that is missing from `ROAD_LOOKS` is dropped in `_stroke()`, so that road is not drawn at all rather than drawn flat.
- **The scans are photographs and the terrain beside them is a flat colour, so `road_tint` is not optional.** At face value the two asphalts sit at 0.198 and 0.025 in linear against a `ground_color` of 0.168, which is a merely dark road next to a black stripe. The tints (measure them as a `source_color`-decoded mean — `srgb_to_linear` over the whole image, which is the space `ground_color` and the tints are in) put both on the terrain's own brightness so the two asphalts are told apart by grain rather than one being a hole in the map. **A tint is a property of the file it was measured from, so swapping a scan invalidates it**: the coarse asphalt's factor is around 7 and is the one to recompute, since a scan a stop darker silently becomes a dark stripe rather than an error. Which scan goes with which surface is judgement, not something the tags say — the tags only say how big the road is and how loose its surface is. **`surface` beats the class in both directions** (`OsmRoad.SURFACE_LOOSE` *and* `SURFACE_PAVED` both outrank `CLASS_LOOSE`, because a survey is worth more than a default), so the only ways that fall back to their class are the ones that say nothing at all: 380 of the ways in this extract are explicitly paved, and without the `SURFACE_PAVED` half they were drawn as gravel — almost all of them the paved `highway=path`/`footway`/`cycleway` cycleway beside a road, sharing a surface with it.
- **The forest floor's patch noise is its own, not the wave `ground_noise`, and the ramp edges are tied to it.** Sharing one noise was tried and does not work: the wave noise is slow and low-amplitude, so the patch value sat inside a fraction of its range (measured 0.23-0.42 over a wood), which put the whole floor in one texture and the grass band nowhere. `OsmGroundData._make_forest_noise()` builds a seamless Simplex volume instead — `seamless` because the uv is world position, or every `forest_patch_m` repeat ends in a hard seam, which is the exact edge the blend exists to avoid. **It is one volume per patch** (`OsmGroundData.FOREST_PATCHES`), not one volume read at two offsets: an offset moves where a patch sits without changing how big it is, and patch size *is* the frequency. **Both `forest_soil_edge` and `forest_grass_edge` sit on the measured distribution, not on 0..1** — `NoiseTexture3D` maps `FastNoiseLite`'s signed output onto 0..1, so a three-octave simplex lands in about 0.10..0.89 with half of it inside 0.40..0.60. An edge pair **below 0.10 is under the whole volume**, which is the failure worth naming: `smoothstep` returns 1 for every fragment, and the patches come out as one flat blend instead of patches at all.
- **`AREA_BONUS_M` is where the area layer's budget is actually decided.** Water holds 1200 m because a lake is a handful of features that would otherwise lose every contest. Forest holds 120 m for the same reason in miniature: trees are planted from `OsmForestArea` whether or not their ground draws, so a wood whose ring is dropped reads as bare grass under a canopy. Measured at the spawn in edges of 576: no forest bonus gives forest 141 / farmland 165, a 400 m bonus gives forest 343 and **farmland nothing at all**, 120 m gives forest 193 / farmland 141. Raise it if woods come back bare, lower it if fields start vanishing.
- **`RING_EDGE_BUDGET` caps a wood's outline at 40 edges** against the 160 every other kind gets. A forest ring is the largest on the map, is drawn as a floor that fades over `forest_fade_m`, and sits under a canopy that hides its edge — so the detail is spent where nobody can see it, while the fields it competes with for the same 576 edges are what actually need them.
- **The parity is per kind on purpose.** Farmland rings overlap meadow rings constantly; one crossing count shared between them cancels both to nothing across the whole overlap. The same-kind case that is still wrong — two rings of one kind overlapping — is the trade water already made, which is why it has its own function.
- **`cover_fade_m` is a per-kind edge feather, and it is only as good as `nearest_sq`.** The distance is a min over every edge of that kind in the upload, which is what you want at a boundary (the nearest edge of that kind *is* the boundary) and means a fragment deep inside a field also answers to a neighbour's edge. Two kinds with bare ground between them cross-fade through it, which is the point — but a mask that comes out as a bare 0/1 step means `nearest_sq` never got written, not that the fade is too narrow. See the note in `area_masks()` about why it is written out per component rather than steered by a one-hot vec4.
- The two uniform arrays put the kind in **different components** (`area_attrs[i].x`, `line_attrs[i].y`) — see the note on `OsmGroundData._fill`.
- `upload()` keeps the **nearest** N, so the caps *are* the visible distance: the horizon is how far the marginal entry reaches, not the cap and not `DETAIL_RADIUS`. Raising the caps without raising `LOAD_RADIUS`/the camera far plane buys nothing.
- `Layer.points` is the unsorted candidate list. To check what the shader actually got, read back `material.get_shader_parameter("area_points")`.
- `type=multipolygon` relations are stitched into ways in `OsmDataset._multipolygon_ways()` *before* the tag filter, and an `inner` chain becomes its own way with the same tags so islands read as land. A lake the size of Roxen is a relation, not a closed way.
- **The ground scans need `mipmaps/generate=true`** (`assets/textures/ground/*.jpg.import`). Godot's 2D default is off, and a tiled ground texture is the worst case for it: at `cover_tile_m` metres per tile a 1K scan goes fine detail to nothing within a few metres, and with no mip chain to fall back on it aliases into regular diagonal corduroy rather than soil. Keep `detect_3d/compress_to=0` here for the same reason as the DEM: the editor rewrites the mode under you otherwise.

**Forest trees** — a stand is grown in two ages, and they are separate meshes.
- `ForestGen.TreeAge` is `Adult` or `Young`, and the builders are split by age into `scripts/treegenerator/presets/`: the grown trees in `TreeGenPresetsAdult` (`adult.gd`), the saplings in `TreeGenPresetsYoung` (`young.gd`), and the bark and leaf textures plus the base-tree helper they share in `TreeGenPresetsCommon` (`common.gd`). **The two age files share only those assets** — a sapling is a tree of its own with its own branches, not the adult's parameters changed and never a scaled adult mesh, so it has its own silhouette. What makes it read as one: a short thin stem, a crown that starts low down, one branch level fewer than the adult, and more but smaller leaves.
- **A sapling's leaf count has to survive the LOD cut on its own.** `ForestGen._apply_lod` keeps `max(3, leaf_count * 0.12)` leaves per twig, so a preset below ~25 leaves per twig lands on the floor of 3 and the crown comes out as sparse as the adult's — the young presets carry ~44-48 for that reason, not because the hero tree needs them.
- **A mesh is baked per (species, age) pair, not per species.** The pair is a `Vector2i` key in `ForestGen._meshes` and `_wanted_count`; dropping the age from that key makes the saplings overwrite the adults' meshes, and the stand comes up with a canopy and no understory under it.
- `FOREST_TYPE_TREES` counts densities per age as well as per species, so a stand's understory is a separate decision from its canopy. `ForestStreamer` waits for both ages' meshes before it plants a cell (`needs_ready`), which is what keeps a cell from arriving as a bare canopy with the saplings trailing in behind it.
- **The tree count comes from the forest's area in the cell, not from the cell's area.** `ForestRegion.forest_area` is the forest's outline clipped to the cell, so the densities in `FOREST_TYPE_TREES` really are trees per square metre *of forest*. Counting from the cell instead gave a cell that clipped the corner of a wood a whole cell's worth of trees to stand in that corner, and that is what grew one trunk through another. **The clip has to be made in world metres**: Clipper resolves to 1e-5 of the input's magnitude, so a cut made in degrees is a cut made with a centimetre's worth of precision and the areas come out wrong by tens of percent.
- **The trunk gap is held across a cell boundary by a margin, not by the cells knowing about each other.** `ForestCell.BORDER_MARGIN_M` keeps every tree half a gap (plus a cushion) inside its own cell, so two trees in neighbouring cells are a whole gap apart without either cell having to know the other exists. A shared occupancy grid would hold the gap too, and would break the invariant that a tree never moves because a neighbour streamed in or out: with a shared grid a cell's trees would depend on which cells happen to be live.
- **Undergrowth is spread by its own gap and its own grid, not by the trunk gap.** Grass and fern have no trunks to grow into each other and grow at a tree's foot, so `ForestCell.MIN_UNDERGROWTH_GAP_M` (0.35 m) and the second bucket grid keep patches of undergrowth apart — running them through `MIN_TRUNK_GAP_M` is what used to hold every tuft 1.7 m from every other, a sparse lattice rather than dense grass. The undergrowth densities in `FOREST_TYPE_TREES` are therefore **patches** per m², not blades: one instance carries a whole patch (`TreeGenPresetsUndergrowth.PATCH_BLADES` over `PATCH_RADIUS_M`, ~100 triangles), and the two numbers are kept in step with `MIN_UNDERGROWTH_GAP_M` by hand. **Undergrowth is also the one plant that may stand in `BORDER_MARGIN_M`'s band along a cell edge** (`ForestCell.can_plant_undergrowth()` checks the whole cell): the margin is a rule `can_plant()` enforces on trees, not something the region is cut by (`ForestRegion.clip()` takes the whole cell), because a band of ground with no grass in it is a bare lane down every cell boundary — visible as a grid of 32 m squares. Cutting the margin out of the clip instead would put the lane straight back.
- **A leaf's pale side is its *front* face, and the knob for it is `TreeGenMaterialLibrary.UNDERSIDE_TINT`.** Every strip — tree leaf, fern pinna, grass blade — is one double-sided quad carrying a single up-tilted normal, and the engine flips that normal for the back face; so the front face (the one the up-tilted normal lights) is the pale one and the back face is the dark one. That is backwards from a real leaf, and it is what puts a pale green under the ferns and on some blades. The leaf material is therefore `leaf.gdshader` rather than a StandardMaterial3D — a StandardMaterial3D has no per-facing albedo — with the tint on the front face and defaulting to white, which measured pixel-identical to the old material. The alpha cutoff is a literal in the shader that has to match `LEAF_ALPHA_CUTOFF` by hand, and a `NORMAL` written in the fragment stage cancels the engine's flip instead of adding to it, which lights both faces alike.
- **The count and the planting area are deliberately two different numbers.** The count comes from the forest's area in the whole cell, while the trees stand in the cell with the margin taken off it — about a tenth of the cell — so a cell that lies wholly inside a wood plants its density into a slightly smaller area. That standing area is a rule `ForestCell.can_plant()` enforces, not a cut made in the region: the region is clipped to the whole cell, so that the undergrowth, which keeps no margin, can stand in the band.
- **A tree may not stand on anything that is drawn on the ground.** `ForestCell.BLOCKER_GROUPS` is roads, railways, water, buildings and cover. A line blocks half its width plus `CLEARANCE_M`; an area blocks its own interior and the clearance around its edge. The features are gathered from `GATHER_MARGIN_M` beyond the cell, which has to be more than half the widest way in the extract plus the clearance (the widest is 40 m, so 21 m) — a road whose tarmac reaches into the cell but whose way does not would not be gathered, and the trees standing on it would not know. **Undergrowth answers to the same blockers with its own reach added on top** (`ForestCell.can_plant_undergrowth(spot, reach_m)`): the clearance is measured to the plant's origin, while a patch's blades, a fern's fronds and a boulder's lobes lean out past it, so at a bare `CLEARANCE_M` the origin sits a metre from the water and the blades are standing in it. The three constants — `TreeGenPresetsUndergrowth.GRASS_REACH_M` (arithmetic over the blade's lean and width), `FERN_REACH_M` and `ROCK_REACH_M` (measured over hundreds and thousands of baked seeds) — are what that reach is, and they are derived from the geometry they describe: grow a patch's radius or its size range without revisiting them and plants quietly go back onto the tarmac and into the water. Trees keep the bare clearance — a trunk is what `CLEARANCE_M` measures and the crown overhangs where it stands.
- **An `inner` ring of a forest is a clearing, not a wood.** A multipolygon relation is stitched into one way per ring, and the rings that are holes come out as forests of their own with the relation's tags, so the clearing in the middle of a wood would be planted with the wood. `OsmWay.role` and `OsmFeature.is_hole()` say which ring is which, and `ForestStreamer._plan_for` skips the holes. The ground shader gets this right by itself, because the forest floor is one parity count over every forest edge and a hole crosses it twice; the trees have to be told.
- **A tree's spot is the best of a batch, not a plain draw.** `ForestGen._pick_spot` takes the best of `CANDIDATES` spots, scored by their distance to the nearest tree already planted in the cell. Without it the trees are a plain random walk and a wood comes out in patches with bare ground between them rather than evenly spread.

**Runtime wiring** — `main.gd` builds everything not in `main.tscn` and is where test content lives.
- Setting the spawn takes two steps in a fixed order: `_place_player_at_lonlat()` in `_ready()` **before** `set_stream_target()` (it decides which tiles load), and `_snap_player_to_ground()` in the **first `_process()`** (a raycast cannot see collision shapes the physics server has not stepped yet — from `_ready()` it comes back empty every time).
- `camera.far` is set from `Heightmap.LOAD_RADIUS * 0.96` in `main.gd` to keep the streamed disc's ragged edge off screen.

## Gotchas

- **GDScript warnings print nowhere.** Not in a smoke run, not under `--headless`, not with `--check-only --script` — the analyzer keeps them in the script editor's warnings panel and writes nothing to the console, so a clean run says nothing about them and `--verbose` does not help. The LSP is the only machine-readable source (Commands). Expect them in the places the style above already answers for: a parameter that shares a member's name (`p_`-prefix it, as `OsmQuadtree` and `OsmGroundData.bind` do), a local named after a `Node3D` property (`position`, `scale`, `basis`, `transform`, `ready`), and a variable named after a global function (`seed`) — those are all renames, not suppressions.
- **`--headless` does compile `ground.gdshader`** — `RendererDummy` still runs the shader compiler, and a type or syntax error comes back as `SHADER ERROR` with a line number. It is the *windowed* run that a clean headless run does not replace: only that prints `Using Device`, and only that exercises the real GPU path. Compile it windowed (~3 s on `DISPLAY=:0`) and look for `Using Device` plus any `Shader compilation failed`. Shader-language rules that bite: a function may only be called from a function **below** it, and uniform array sizes must be literals.
- **`MultiMesh` instance data is a no-op under `--headless`** — transforms silently stay identity and AABBs are empty, so every tree reads as being at the origin. Only `instance_count` and the mesh's own vertex counts are trustworthy headless; verify placement by rendering and differencing the images.
- There is no display feedback here, so verify visuals by saving `get_viewport().get_texture().get_image().save_png(...)` from a frame counter and probing the PNG. Flat debug colours plus a white `AMBIENT_SOURCE_COLOR`/`TONE_MAPPER_LINEAR` environment make it unambiguous — with the scene's own sky-only ambient (there is **no** `DirectionalLight3D`) a probe on the real albedo is unreliable. Aim the `Camera3D` directly: the brackeys controller owns its yaw/pitch and overwrites `ProtoController.rotation`.
- Trees are placed by raycasting the terrain, which only hits inside the streamed `LOAD_RADIUS`, and hits *anything* in the way (including the player's own capsule). Changing height normalization or the heightmap's scale/centering makes forests float or sink.
- **Buildings ask `Heightmap.height_at_world()` for their ground instead of raycasting** (`BuildingGen`). A raycast here would hit a neighbouring building's collider or the player's capsule and stack one on top of the other; the height map needs no physics and no step order. It rounds to a pixel centre where the collider interpolates, so the walls are sunk by `GROUND_SINK`.
- Free-fly is the `freefly` action bound to **physical keycode 59** (the `Ö` key on a Swedish layout), not a letter. Remap in the Input Map tab.
- Startup: ~0.35 s to index the extracted features, then ~0.5 s per generated forest. Lower the loop cap in `main.gd` when iterating on placement.
