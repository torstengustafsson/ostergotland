# AGENTS.md

Godot 4.7.1 (GDScript) 3D terrain demo of Östergötland, Sweden (Kimstad area). No tests, no CI, no linter/formatter.

## Commands

- Godot binary: `/home/torsten/Godot/Godot_v4.7.1-stable_linux.x86_64` (also in `.vscode/settings.json`). Do **not** use the sibling `Godot_v4.6-stable_linux.x86_64` — it would clobber 4.7 features in `project.godot`/`.import`.
- Run: `godot --path .`, or open `main.tscn` in the editor.
- No test suite, so verify with a headless smoke run: `<binary> --headless --quit-after 3`. It boots `main.tscn` and prints load/generation timings. Exit-time noise (`3 resources still in use at exit`, `ObjectDB instances were leaked`) is pre-existing and harmless.
- `<binary> --headless --import` regenerates `.uid`/`.import` files after adding, renaming or duplicating scripts/assets — no need to open the editor.
- `opencode.json` denies `git *` for the bash tool: don't try to run git commands.
- `python3 assets/heightmap/osm_to_json.py` regenerates `ways.json` from `ways.osm` (stdlib only; the current `ways.osm` is ~55 MB and takes a while). Run it from the repo root; paths are resolved relative to the script.
- **Never give a verification run a timeout above 30 s** unless it genuinely needs one. A smoke run is ~1.5 s and a shader-compile check ~3 s, so a longer timeout is not slack to be spent on them. That limit is not arbitrary: it exists so that a *hung* run is cheap and obvious rather than something to wait out. Every run here should be wrapped as `timeout 30 <binary> ...`, and a timeout means one of three things, all of which are bugs to look at rather than a number to raise:
  1. **A one-shot signal was awaited after it had already fired.** `await RenderingServer.frame_post_draw` does exactly this and blocks forever if the frame was already presented — capture the viewport in a later `_process` instead, no `await`.
  2. **Something never terminates.** Check what the run actually printed before the cut-off; the last line is where it stopped.
  3. **`--fixed-fps` was left on.** It pins `delta` to `1/n`, so every frame reports the same time no matter the load and any measurement taken with it is meaningless. Only for reproducible screenshots, never for timing.
- A run that genuinely needs more time is a finding, not a convenience: say so and say why, rather than quietly widening the timeout until it passes.

## Code style

**Comments are for the non-obvious and nothing else.** A comment earns its place only when it says something the code does not: why a sign is flipped, which order two calls must run in, what a number was chosen to fit, what breaks silently if it is changed. Measure against that, and the rule is short: one to three lines per comment block, or none at all.

- **No comment for what the code already says.** Narrating the next line, restating the signature, or writing `# loop over the cells` above a `for` costs the reader and buys nothing.
- **No comment for the bug you already fixed.** "This used to do X", a benchmark table, a post-mortem of a broken state, a history of the refactor — that is what this file is for, and most of it is already here. Duplicating it into the source is how `heightmap.gd` and `osm_ground_data.gd` ended up with more comment lines than code.
- **Document the constraint, not the fix.** Say what bounds a number (a uniform-buffer ceiling, a measured cost) and why a particular expression is the right one, rather than explaining the obvious arithmetic next to it.
- **Doc comments (`##`) are for the module and for anything a caller must know before using it** — the coordinate space, the units, the ordering requirement. Two or three lines. A param table belongs in the module doc; a `##` on every self-explanatory accessor does not.
- **Kept on purpose:** the sign/order conventions with no other source of truth (`+Z` is south, the winding, the reversed collision rows, the kind in `.x` vs `.y`), the "whole ring or nothing" rule, and the reach gates. These fail silently when wrong, and that is exactly the bar.

**Every text file ends with a newline, always.** No exception for a one-line file or a generated one — `osm_to_json.py` appends it on write. `.editorconfig` sets `insert_final_newline` so an editor cannot undo it, and `\ No newline at end of file` is not a thing to leave in a diff. Binary assets (`.exr`, `.mp3`, `.png`, `.jpg`) are the only files exempt, because a byte there is data rather than formatting.

The target ratio is well under one comment line per two lines of code. Parameter tables in `treegenerator/` (one `##` per field) are the exception and are fine.

## Scene / runtime wiring

- `main.tscn`: `Main` (Node3D + `scripts/main.gd`, which itself `extends Node`) → `Heightmap` (StaticBody3D running `scripts/heightmap.gd`, with no children of its own — it builds its tiles in code), plus `ProtoController` (brackeys addon instance), `WorldEnvironment`, and a HUD `Label`. `sprint_speed`/`freefly_speed` (15 / 120 m/s) are set in the scene file, not the addon.
- `main.gd` builds everything else in code (`OsmDataset`, `OsmQuadtree`, `OsmGroundData`, `ForestGen`, `AudioManager`) and is where all test content lives: `$Heightmap.set_stream_target($ProtoController)`, birdsong at the origin, wind on the camera, forests near the player (via `osm_index.query_rect(...)` + `osm_index.entry_points(...)`), and the `features_near_player()` example query.
- **The spawn is a lon/lat (`SPAWN_LONLAT`) and setting it takes two steps in a fixed order**, because each half needs what the other one produces: `_place_player_at_lonlat()` projects it through `OsmProjection` for XZ and has to run in `_ready()` *before* `set_stream_target()`, since it decides which tiles get streamed; `_snap_player_to_ground()` raycasts down onto the collider for Y and has to run in the *first `_process()`*, since a raycast cannot see collision shapes the physics server has not had a step with yet — from `_ready()` it comes back empty every time, because the terrain's own tiles were added in that same frame. The player is excluded from its own cast or the ray answers with the capsule's 1.8 m. `height_at_world()` would do instead (it needs no physics and no ordering) and lands 8 cm off, since it rounds to a pixel centre where the collider interpolates across the cell.
- `heightmap.gd` streams the terrain: it reads the EXR once into a flat float array (the `Image` is dropped afterwards; the array holds exactly what `get_pixel().r` returned, verified pixel for pixel) and builds 64 px square tiles around a focus point — a tile is one `ArrayMesh` + one `CollisionShape3D` child of the `Heightmap` body, both centred on that tile. `set_stream_target($ProtoController)` streams after a node every frame and builds the first tiles synchronously, before the forest loop's raycasts. `TILE_SIZE` 64 px is about 1.0 km east-west and 2.0 km north-south here, and ≈ 4 ms per tile (`LOAD_RADIUS` 2500 / `UNLOAD_RADIUS` 3200 metres); 230 tiles cover the whole 1431×622 grid, 19 of them load around the start. `LOAD_RADIUS` is the view distance and the frame budget scales with it, and it is no longer pinned to the camera: **main.gd sets `camera.far = Heightmap.LOAD_RADIUS * 0.96`**, which is what keeps the terrain's edge off screen now that the two are independent. It is safe to do that because the loaded set is contiguous: a tile is loaded when the *focus is within `LOAD_RADIUS` of its rect*, so an unloaded tile is never crossed by any ray inside that radius and terrain exists everywhere within it. Grid size comes from the EXR and `width`/`height` always describe the whole grid, so main.gd's `OsmProjection` is unaffected. Physics engine is Jolt (`project.godot`).
- **The world is in metres, one world unit per metre on all three axes, and nothing in the terrain's scale is hardcoded** — see the next bullet, which is where the horizontal comes from, and `HEIGHT_NORMALIZATION`/`HEIGHT_SCALE` (1000 / 1.0), which is where the vertical comes from. The node's scale is `Vector3(cell_size.x, HEIGHT_SCALE, cell_size.y)`, set in `_apply_scale()` from `cell_size` (16.145, 30.949 m) once the EXR has been read, so nothing may read `scale` or `cell_size` before `_ready()` has run. Godot's default gravity, the camera far plane and the addon's speeds are then all in their intended units for free; the freefly speed in `main.tscn` is 120 m/s (500 was 20× too fast once a unit became a metre).
- `cell_size` comes from the DEM's own lon/lat extent: `OsmBounds.from_file(res://assets/heightmap/coordinates_bounds)` then `OsmBounds.cell_size_m(grid_size)`, which is the lon span × 111320 × cos(centre lat) over the cell count on X and the lat span × 111320 over it on Z. A degree of longitude is cos(latitude) times as long as a degree of latitude, so the two axes differ by 1.9× here and **a single `CELL_SIZE` for both is the bug that made the landscape twice as wide as it is deep** — the grid is 23 087 m east-west by 19 220 m north-south, not square in metres. Both the terrain and `OsmProjection.metres_per_unit` go through that one function, so `metres_per_unit` is now exactly `(1, 1)` and the terrain's world extent and `OsmProjection.world_bounds().size` agree to the float.
- `_height()` is the only place the EXR's raw values get divided by `HEIGHT_NORMALIZATION`, and the mesh, the collision shapes and the normals all go through it. **The raw values are millimetres** (the grid's highest is 154 183.69, i.e. 154.18 m; the median is 6.0 m), so `HEIGHT_NORMALIZATION` is 1000 and using the raw values directly puts the mesh tens of thousands of metres above its collider: the player, the forests and the collision all look correct while the terrain is invisible *from any direction*, because its top is far past the 4000 far plane and its underside is back-facing. Three things have to agree on that scaling: the mesh vertex y, `map_data`, and the middle component of `_normal_at`. That one is `2.0 * HEIGHT_SCALE` and stays exact under the per-axis scale, because a difference in X spans one cell and the node's X scale *is* the cell size in metres, so the cell size cancels out of the horizontal part of the inverse-transpose — with one `CELL_SIZE` for both axes it did not cancel, and squashed lighting was the symptom. Verified: the world-space normals match a gradient taken straight from the heights in metres to 3e-4, and the mesh vertices match `height_at_world()` to 2 µm over every loaded tile.
- `update_stream()` measures in **world metres, not source pixels** (`_tile_world_rect()` / `_rect_distance()`). In pixels the two axes are a different number of metres per cell, so one radius would load twice as far east-west as north-south; `_tile_world_rect()` also has to subtract `_grid_origin_offset()`, since without it the rects are measured from the grid's own corner and on a 23 km grid even the tiles under the focus read as 6 km away (it streams 9 wrong tiles instead of 38 right ones).
- `HeightMapShape3D`'s origin is not documented, so it was measured: data index `i` sits at local `i - (map_width - 1) / 2` (a 4×4 grid spans exactly -1.5..+1.5) and the row index runs along **+Z**. A tile's shape is therefore `cols + 2` wide, sits on the same `center` as its mesh, and the one-cell overlap has to be symmetric — the mesh's 65 pixels become data indices 1..65, not 0..64.
- A tile's **mesh** spans `TILE_SIZE + 1` columns, not `TILE_SIZE`: tile *t* covers source columns `64t … 64t+64` so it and tile *t+1* share the vertices of their common edge. With 64 columns the meshes stop one cell apart and every seam becomes a 10-unit slot — a hole in the terrain that reads as a brown line, because the sky's `ground_bottom_color` is brown. The collision shapes were always `cols + 2` wide, which is why physics looked right while the render had holes; a seam only disappears when both halves agree, so check the vertex count (`65x65`) and the gap between two neighbouring tiles' edge vertices if the grid shows up again.
- Two things the tiles have to get right, both easy to break: a tile's mesh uses the **analytic height-field gradient** for normals, not `SurfaceTool.generate_normals()` (averaging inside a tile would light shared edges differently and draw the tile grid onto the landscape), and its collision shape is one cell wider/deeper than the mesh so neighbouring shapes overlap at identical heights — without that overlap, raycasts and falling players find cracks at the seams. UVs stay global (over the whole grid), which is what they were for: the shader no longer samples any texture with them, but it does place its features by **world** XZ, so nothing may move a tile's mesh off the grid.
- The triangles must be wound **clockwise seen from above** (`(i0, i0+1, i0+cols)` per cell, as the single big mesh was). Godot treats that side as the front face, so the reverse order renders a fully culled, invisible terrain while the collision still works — which is exactly how it looks, so a tile that "has" a mesh can still be invisible. `generate_normals()` on a flat test tile is the cheap way to check which side Godot considers front.
- No mask textures are loaded, and none are declared any more. `ground.gdshader` draws its features straight from the OSM geometry: `OsmGroundData` packs the ways near the player into uniform arrays and the shader measures each fragment against them, so road widths come from the tags instead of a raster mask. (Before that, the four `*_texture` samplers were declared but never set, and an unset `sampler2D` samples **white** — that is what left the terrain a flat `rail_color` grey.) `assets/heightmap/filter_mask.py` is orphaned: it reads `viz.hh_aspect.png`, which no longer exists, and needs Pillow unlike `osm_to_json.py`.
- The ground shader's arrays are `line_points`/`line_attrs`/`line_count` (**1408**) and `area_points`/`area_attrs`/`area_count` (**512**): `(ax, az, bx, bz)` metres per entry, `line_attrs` = `(half_width, kind, reach)` and `area_attrs` = `(kind, 0, reach)`. The **fourth attrs component is the distance from the focus to that entry's farthest point**, which is the single most valuable byte in there — see the reach gate below. The sizes are in `OsmGroundData.MAX_LINES`/`MAX_AREA_EDGES` and **must match the four `uniform vec4 ...[n]` declarations in the shader** — that is now the *only* place they appear, because the three loops bound themselves on `line_count`/`area_count` instead of repeating the literal. That matters more than it looks: a resize where only the declarations were updated leaves the loops testing the old number, which draws the old picture with no error anywhere. Every entry costs a points and an attrs vec4, so 32 bytes, and 1920 entries is 60 KB of uniform buffer. The ceiling is the device's `LIMIT_MAX_UNIFORM_BUFFER_SIZE`, measured at **65 536 B on this machine's RTX 4060** (`RenderingDevice.limit_get(RenderingDevice.LIMIT_MAX_UNIFORM_BUFFER_SIZE)`, not the spec minimum), so 4 KB is spare; Vulkan only *guarantees* 16 KB, which is 512 entries, so this now needs a real GPU and would fail pipeline creation on a minimum-spec one rather than degrade. 1536/512 does fit in 64 KB exactly and halves the frame rate, which is where "as high as reasonable" stops. Everything works in metres: `OsmGroundData` uploads `metres_per_unit`, which is `(1, 1)` now that the world is, and the shader multiplies the world XZ by it. The uniform stays because it is the one place that knows how to convert, in case the terrain stops being metres.
- **The caps *are* the visible distance, and it is not linear.** `upload()` keeps the *nearest* N, so the farthest thing drawn is the marginal entry: measured at the spawn, 144/96 → `line_reach` 303 m, 576/384 → 772 m, 1280/512 → 1211 m, 1408/512 → **1393 m**. So the shipped 1408 reaches almost exactly the 1440 m far plane (`LOAD_RADIUS * 0.96`) and no cap can usefully exceed it without also raising that. Cost on the 4060 at 1280×720, camera raised to 400 m so the ground fills the frame, vsync off: 57 KB → 117-119 FPS, 60 KB → 103-115, 64 KB → 66. **The area caps are the same kind of lever but the sort decides what they hold**: `area_reach` was stuck at 411 m from 96 edges to 512 alike, because rings sort by their *nearest* side and the farthest side of the Nth-nearest ring was just however big the biggest shed near you is. Raising `AREA_BONUS_M[AREA_WATER]` to 1200 m (it was 250) is what moved it: 411 m → 1514-1800 m, three of the six lakes in `DETAIL_RADIUS` instead of one, at a cost of 20 building edges out of 512.
- **The two uniform arrays put the feature's kind in *different components*, and that is not a detail.** `line_attrs` is `(half_width, kind, rank, reach)` and `area_attrs` is `(kind, 0, 0, reach)` — the shader reads `area_attrs[i].x` and `line_attrs[i].y` — while `_fill` builds its attr with the kind in `.y`, i.e. following the *line* convention. `upload()` copies `.x/.y/.z` straight through, so every filled area arrived with kind `0.0` == `AREA_BUILDING`: **no lake, pond or reservoir was ever filled as water**, they were all painted as if they were buildings, and `water_area_mask()` (which `continue`s on anything that is not `AREA_WATER`) skipped every edge in the array, so nothing sank or rippled either. Roads and watercourses were fine throughout, which is why it read as "water works" — the blue in a screenshot was a stroked `waterway`, never a filled one. Verified by checking each ring's own vertices against the uploaded array rather than by eye: all six rings near the spawn are in it.
- What the shader does with the arrays: every line is a stroked segment at `half_width` with a 0.6 m feather, and overlapping features take the strongest coverage (`max`), not a sum, so a footway across a motorway leaves a motorway; `rank` tints roads a little. Filled areas use an even-odd crossing test per edge (one crossing test per fragment per entry), with the distance to the nearest edge antialiasing it — the sign comes from the crossing test, so no signed distance is needed, and two overlapping rings of the same kind cancel out exactly as they did in the mask. Filled water alone is also tested per **vertex** (to sink the ground and ripple it); watercourses are thinner than a terrain cell, so a per-vertex test would mostly miss them and the fragment stage covers them instead. Water areas are therefore the only thing that moves terrain, and their wave noise is sampled in **world** space — sampling `VERTEX` instead repeats the pattern exactly once per streamed tile.
- **A filled area is uploaded whole or not at all** (`Layer.add_ring`, candidates are groups: one segment for a line, a whole ring for an area). The crossing test counts how many ring sides a ray crosses, so one missing side inverts the answer *everywhere* that side used to close the ring: the fill floods to infinity past the feature's real edge instead of stopping at it, and its boundary reads as a straight coloured line across the map that moves as you walk. That is what a building's red turned into. So `OsmGroundData._fill` also skips a ring whose farthest side is beyond reach, and `Layer.upload()` skips a group that will not fit whole rather than truncating one. A ring that is missing entirely is invisible; a half ring paints the world. Lines are unaffected — each segment stands alone, so nearest-first per segment is correct there.
- Lines are also length-capped (`MAX_SEGMENT_UNITS`, the detail square's diagonal ~1697 units): a two-node way kilometres long is a placeholder, not a shape, and stroking it paints a straight stripe to the horizon. It is what the `waterway=flowline` ways in this dump are (up to 6425 units long); the longest real feature is a 1306 unit railway, well inside the limit.
- `OsmGroundData` gathers a square `DETAIL_RADIUS` (1800 m) around the focus and keeps the **nearest** entries when a layer overflows (`KIND_BONUS_M`/`AREA_BONUS_M`/`RANK_BONUS_M` in metres are only tie-breakers between kinds — a railway or a lake is a handful of features in a village full of roads and would otherwise never make it in; the water bonus is the one that has to be large, in metres, because that is what decides whether a lake 1.5 km away beats a shed 1 km away). `REBUILD_MOVE` (50 m) throttles repacking, so `update()` is safe to call every frame. Packing costs ~10 ms for a full square here (it was 2 ms at a 600 m radius); `dropped` counts groups, so the area figure is rings, not edges.
- **The ground shader is the frame budget**, and the numbers are worth having before anything else is blamed. Measured at 1280×720 on this machine's software renderer (llvmpipe, no GPU): sky and terrain-free 8 ms, the 38 terrain tiles with a flat material 31 ms, the ground shader on top of that 95 ms, the 4355 forest trees 132 ms. So of ~130 ms the OSM feature loops are ~64 ms, the trees ~36 ms and the terrain raster ~23 ms. Two consequences: the scale change is not what made it slow (at the old single `CELL_SIZE` of 30 units the same view cost 134 ms), and the thing to reach for when it feels slow is `MAX_LINES`/`MAX_AREA_EDGES` or the tree densities, not the terrain.
- **The feature loops are gated on how far the features actually reach** (`focus_metres`, `line_reach`, `area_reach`), and this is the one perf fix here that is free: it took the shader from 133 ms to 95 ms and the two renders are **byte-identical**. `Layer.upload()` writes the focus and the largest reach it chose into those three uniforms, and `line_masks()` additionally skips an entry per entry on `line_attrs.w`. It is exact rather than approximate: nothing uploaded is drawn past its own reach, so a fragment or vertex beyond it provably cannot be inside any of it. Note that gating only buys what it can — the near ground fills the whole lower half of the screen, so roughly half the fragments legitimately run the loops no matter how tight the gate is, and the cost then scales linearly with the entry count, measured on llvmpipe at 1280x720: 288/192 → 99 ms, 144/96 → 65, 96/64 → 56, 48/32 → 43, none at all → 34. Those are software-renderer numbers and the caps have since gone to 1408/512 (see above), so the budget is spent on the 4060's 103-115 FPS rather than 60 on llvmpipe. `LOAD_RADIUS` also came down to 2500 m on top of the gating: 133 ms at the start of all this on llvmpipe.
- **`water_area_mask()` runs per vertex, not per fragment**, which is why it dominated before the reach gate: 192 crossing tests for every grid point of every streamed tile, 160k of them, on a cost that does not depend on the resolution at all. Watercourses are thinner than a terrain cell so it cannot move to the fragment stage, but the reach gate takes it out of the picture for the ~99% of vertices that are nowhere near the packed water.
- **Terrain LOD is implemented and it does not help here**: tiles past `LOD_DISTANCE` (700 m) build their mesh at `LOD_STRIDE` (every 2nd source pixel), which really does cut the loaded disc from 80 275 vertices to 33 235 (15 of 19 tiles coarse, a 2.4x cut). Measured frame time with 20-frame samples: 78.6 ms at full resolution vs 74.2 ms with every tile coarse -- **4%, i.e. nothing**, and within noise of the 78.9 ms the shipped setting gives. So the cost is neither per-vertex nor per-fragment in any way that this change touches, and 60 FPS at 1280x720 on llvmpipe is not reachable by decimating terrain. It is kept because it is correct and cheap, and vertex cost *is* real on a GPU.
- The frame is **~75 ms at 1280x720 and ~45 ms at 640x360**, and the components at 1280x720 (settled: all bakes finished, 30-frame warm-up) are: ground shader ~34 ms, trees ~18 ms, terrain tiles ~15 ms, base ~8 ms. Note that the ground shader is flat in resolution (33 ms at 640x360 vs 34 ms at 1280x720) even though a third of it is per-vertex and a third per-fragment, so the resolution/vertex experiments above disagree with each other and neither is a reliable guide to it; measure before believing either.
- **Bigger `TILE_SIZE` does not make it faster**, though it is the obvious thing to reach for when the tile count goes up (measured at the old 4000 m radius): 38 tiles / 160 550 vertices / 20 draws / 97 ms at 64, 21 / 197 589 / 14 / 101 at 96, 15 / 249 615 / 10 / 107 at 128, 9 / 335 241 / 8 / 112 at 192. Two things make it worse rather than neutral. A tile is built as soon as *any* of it is inside `LOAD_RADIUS`, so a bigger one overshoots the circle and the vertex count goes **up**, not flat -- the total is only fixed by resolution if the tiles tessellate the disc exactly, which they never do. And the draw calls it saves are worth nothing here: the cost is per-vertex and per-raster work, and llvmpipe does not care about the call count.
- The tile count went 21 → 38 → **19** and neither move was about tiles: a 64 px tile was 30 units square before (1030 x 1950 m) and is 16.145 x 30.949 m per cell now (1033 x 1981 m), i.e. always the same ground. It rose to 38 because `LOAD_RADIUS` went from 4000 units (~2150 m east-west) to 4000 m, which is the point of the scale fix, and fell to 19 because it is now 2500 m. `LOAD_RADIUS` is the only tile-side lever and it gives up view, linearly in its area.
- **The caps bind long before the radius does**, which is the thing to know before touching either. The `DETAIL_RADIUS` square is a candidate *pool*; the visible horizon is how far the nearest N entries reach, because the caps hold a few percent of the candidates. So `DETAIL_RADIUS` only has to be a little past the reach the caps buy — at the spawn 1800 m gives the same 1393 m of line reach as 2000 m for 10 ms of packing instead of 12 — while 600 m cannot supply a 1393 m reach at all however large the caps are. `REBUILD_MOVE` is the knob for the pack's frame-time hitch, not the radius.
- **`Layer.points` is the candidate list, not what the shader got.** `upload()` sorts, fits and copies into fresh arrays that exist only as the material's `area_points`/`area_count` shader parameters, so anything verifying the packing has to read those back with `material.get_shader_parameter("area_points")` — the first `count` entries of `points` are unsorted candidates and will disagree with the shader, which is how the flood above survived a first round of tests that read the wrong array.
- `main.gd` wires it up after the terrain has streamed: `osm_ground.bind($Heightmap.material, osm_index)` then `osm_ground.update($ProtoController.position, true)`, and `update()` again in `_process`. `Heightmap.material` is public for exactly this — every tile shares that one `ShaderMaterial`, which is also why `heightmap.gd` still owns the height uniforms (`MIN_HEIGHT`/`MAX_HEIGHT` = 0/160 metres, the terrain's top being 154.2 m).

## OSM pipeline (`scripts/osmdataset/`)

- `ways.osm` → `osm_to_json.py` → one `ways.json` (`{bounds, nodes, ways, relations}`). Intermediates are committed; no tag-based splitting, all filtering happens at runtime. **Node ids are strings.**
- Runtime: `OsmDataset` (load, `node_position`/`has_node`, `ways_by_tag*`, `extract_features`) + `OsmFeature` subclasses listed in `OsmDataset.feature_classes` (`OsmRoad`, `OsmRailway`, `OsmBuilding`, `OsmWaterArea`, `OsmForestArea`) → `features["roads"|"railways"|"buildings"|"water"|"forests"]`. Adding a feature kind = subclass `OsmFeature`, append to `feature_classes`, call `extract_features()`. `OsmRaster` paints ways into an `Image` mask (hand-rolled Bresenham/scanline fill — Godot 4.7 has no `Image.draw_line`).
- **`type=multipolygon` relations are assembled into ordinary ways before the tag filter runs**, and that is what brings the big lakes in: a lake the size of Roxen is a *relation* in OSM, not a closed way, so while `relations` was kept raw "for completeness" nothing was built from it and all 327 multipolygons here were invisible — the lakes, the forests, the farmland, everything. Three things have to be undone per relation, all in `OsmDataset._multipolygon_ways()`: the member ways are **open segments of the ring**, not closed ways, so they are stitched by shared endpoint (`_stitch()`, and they cannot be read in the order the relation lists them); a chain still open afterwards is **closed by joining its last point to its first**, because this extract is missing member ways (16 of Roxen's 46) and an unclosed ring is the one thing the shader's crossing test cannot survive; and each `inner` chain becomes **its own way with the same tags**, which is what makes islands read as land — the crossing test counts water rings against each other, so a point inside both a lake and one of its islands crosses twice and comes out outside. Measured: 134 filled rings, 129 wholly inside the DEM. **Roxen and Glan are still not *visible*, for reasons that are not about the rings any more**: their outer rings were 2594 and 4269 edges, which is 81 KB and 133 KB of uniform buffer against this GPU's 64 KB — more than a doubled GPU could hold, so they had to be simplified before anything else could work (see the next bullet) — and both lie off the terrain, Roxen 12.2 km west of the DEM's edge and Glan 5.3 km north of it, so `coordinates_bounds` has to grow to roughly lon 15.50–16.15, lat 58.35–58.65.
- **A filled ring is simplified by Douglas-Peucker before it is uploaded** (`OsmGroundData._fit_ring` / `_simplify_ring`), which is what removed that size blocker: Roxen's 2594 edges come out as 150, Glan's 4269 as 148, and both keep 100% of their shoelace area (81.92 -> 81.95 km2 and 73.23 -> 73.06), so what goes is vertices that were already on the chord. Four things about it are not obvious:
  - **A closed ring has to be cut in two.** Douglas-Peucker splits on its two endpoints and a ring has none, so run on the whole loop it is free to collapse half a shoreline onto the chord from first to last — for a lake, a straight line across the middle of it. It is split at its two most distant points and each arc simplified separately, which also preserves the artificial closing segment `_multipolygon_ways()` adds over a missing way.
  - **Recursive is the textbook form and blows the stack** on a 4000-point ring, which is exactly the input this exists for. It is an explicit stack instead.
  - **The tolerance is a starting point, not the rule**: 3 m still leaves ~650 edges, so it doubles until the ring is under `MAX_RING_EDGES` (160). `RING_TOLERANCE_CEILING` stops it, and `upload()` then drops an over-budget ring rather than truncating it, like every other area edge.
  - **The reach pre-test in `_fit_ring` is what made it affordable, not the tolerance search.** Roxen's bbox is stretched by the missing-way gaps so it overlaps the spawn's detail square, and simplifying it there cost 16 ms every repack only for `_fill`'s own reach gate to throw it away; one distance-per-vertex test against `RING_TOLERANCE_CEILING` (exact, since simplification only ever pulls a boundary inwards) takes the pack from **26 ms to 17 ms**. Scaling the tolerance by sqrt(how many points are too many) instead of doubling was measured as *no better* — 20.3 ms either way — so doubling stayed.
  - What is still in the way for a lake bigger than ~3.6 km across is **`DETAIL_RADIUS`**: `_fill` skips any ring whose farthest side is further than 1800 m from the focus, so an 8 km lake is not a candidate unless you are inside it. That is the same rule that keeps the shader's reach gate exact, so it is not a bug to fix but a number to raise, and it costs pack time.
- Every feature carries its own size: `width_m()` (metres, `0.0` when there is nothing to stroke) and `class_rank()` (0/1/2) are what `OsmGroundData` uploads as `half_width`/`rank`, and `is_area()` decides whether a way goes into the area arrays instead. `OsmFeature.explicit_width_m()` reads the `width` tag but only accepts a plain number of metres — imperial (`12'`) and ranges (`3-4`) fall through to the class defaults rather than being guessed at, and `OsmRoad.width_m()` prefers the `width` tag, then `lanes` × 3.25 m, then `DEFAULT_WIDTH_M` for the `highway` value.
- `OsmLanduseBounds` is the container for a landuse area's bounds in every space: `osm_bounds` (lon/lat), `pixel_rect` (terrain grid), `world_rect` (world XZ), and `world_points` (the area's full outline in world XZ — the polygon, not the simplified box). `from_feature()` needs the terrain bounds, grid size and cell size (see `main.gd`, though it now goes through `OsmQuadtree.entry_points()` instead).
- `OsmBounds` also carries the georeferencing the EXR does not: `from_file()` parses `coordinates_bounds`, `is_valid()`, and `cell_size_m(grid_size)` is the one implementation of "how big is this grid in metres" (`METRES_PER_DEGREE = 111320`, times cos(latitude) on X only). `OsmProjection` owns the lon/lat → pixel → world XZ chain (`from_terrain(bounds, grid_w, grid_h, cell_size)`, `to_pixel`, `to_world`, `way_points`, `world_bounds`, `pixel_rect_to_world`) and the **metre** scale the ground shader works in: `metres_per_unit` (a computed getter, `(1, 1)` here, the reciprocal of `OsmBounds.cell_size_m()` over `cell_size`), `to_metres(world)`, `from_metres(metres)`. `OsmLanduseBounds` and `OsmQuadtree` both build one instead of re-deriving the maths.
- `OsmQuadtree` indexes the extracted features in **world XZ** (`Vector2(x, z)`) so gameplay can query by position: `build(dataset, projection, groups = [])`, then `query_rect(rect, group, precise = false)`, `query_circle(center, radius, group, precise = true)`, `query_point(pos, ...)`, plus `entry_rect(feature)`, `entry_points(feature)`, `world_bounds()` and `stats()`. Queries are complete (nothing that touches the area is missed): the default is a bounding-box broad phase, and `precise = true` re-tests the real geometry (segments against the rect/disc, plus point-in-polygon for filled areas) while keeping the bounding box as a cheap pre-reject. `OsmFeature.is_area()` decides whether a closed way counts as a filled polygon — `OsmRoad` overrides it so a roundabout ring is not solid ground. `entry_points()` hands back the same world polyline the index already computed, so placement code does not re-project. ~0.35 s to build the 14410 features here, ~0.2 ms per query.

## Coordinate spaces (easy to get wrong)

- Projection chain: lon/lat → terrain pixel → world XZ, all of it in `OsmProjection`. Pixel→world assumes the grid is centred on the origin with one cell = node scale (`Heightmap._grid_origin_offset()` and `OsmProjection.world_origin_offset()` are the same number and have to stay that way); pixel x maps to world **X** and pixel y to world **Z** with the sign flipped — **row 0 is the northern edge and sits at the *highest* world Z**, so +Z is south.
- **+X is east and +Z is SOUTH, and that is not negotiable: putting +Z = north mirrors the world.** Godot is right-handed, Y up, camera down −Z, screen-right +X, so a non-mirrored world needs forward (−Z) = north and right (+X) = east, i.e. **+Z = south**. The natural thing to write — +Z = north, a map with north at the top — reflects everything: the player spawns facing south and **strafing right moves them east while facing it**, which reads as "the x axis is backwards" even though every coordinate is exactly right and a lon/lat round trip still returns the spawn to the last decimal. Nothing catches it: the OSM/DEM alignment test still passes, because the terrain and the features mirror *together*. The one test that does catch it is to read the camera's basis against the projection — forward into compass terms, screen-right into compass terms, and check that facing south means right = west. Measured before: `faces SOUTH, screen right EAST => MIRRORED`.
- **The mirror is five places in `heightmap.gd` and two in `osm_projection.gd`, and all of them have to move together or the terrain and the OSM features end up mirrored relative to each other** (invisible until you notice the roads no longer follow the ground). In `heightmap.gd`: the tile `center`'s z term, the vertex local z (`y_center - float(y)`, not `float(y) - y_center`), `_build_shape`'s **row order reversed** (`data[(map_depth - 1 - y) * map_width + x]`, because a `HeightMapShape3D` data index still runs along +Z in local space while the mesh's local z now counts *down* the rows), `_normal_at`'s z term (`front - back`), `world_to_pixel`, and `_tile_world_rect`. Two of those are silent and expensive if missed: **the triangle winding reverses** — not cosmetic, it renders a fully culled invisible terrain — and **`_tile_world_rect` streams a mirrored disc**, so the tiles under the focus load but the far ring of the view comes from the other side of the map and the terrain ends well short of the far plane. Verified after the change: handedness correct, lon/lat round trip 0 m over 500 points, all 8 of the biggest water bodies still on DEM low ground, mesh vertices match `height_at_world()` to 0 m over a full-resolution tile, adjacent tiles share their edge vertices to 0 m, 17/17 raycasts down a tile edge hit, and the terrain still renders looking straight down.
- `assets/heightmap/coordinates_bounds` (plain text, `Xmin/Ymin/Xmax/Ymax`) records the heightmap's lon/lat extent: 15.7489 / 58.4698 → 16.1465 / 58.6424. It is **the** terrain extent: `heightmap.gd` parses it (`OsmBounds.from_file`) for the world scale and `main.gd` passes `$Heightmap.bounds` to the projection, so the two cannot disagree.
- `ways.json`'s own `bounds` (15.75 / 58.47 → 16.1465 / 58.64) is a *different* box, up to 0.0024° off in latitude (~270 m), and is no longer used as the terrain's. Passing `osm_dataset.bounds` instead put every OSM feature up to 270 m off the ground; that is what `main.gd` now avoids.
- Two projection rules coexist, and they disagree outside the terrain. `OsmBounds.to_pixel()` rounds to int pixels and clamps, so `OsmRaster` and `OsmLanduseBounds.pixel_rect`/`world_rect` squash anything past the edge onto the border; `OsmProjection` (used by `OsmQuadtree` and `OsmLanduseBounds.world_points`) uses float pixels and does not clamp, keeping the real offset. `ways.json` holds ~20 k nodes outside its own `<bounds>` (lon 14.92–16.65, lat 57.41–59.03), so `OsmQuadtree.world_bounds()` is the terrain grown to reach them, and ~19 of the 1366 forests disagree with their `OsmLanduseBounds.world_rect` by up to ~640 units.
- `ForestStreamer` (`scripts/forestgenerator/forest_streamer.gd`) plants the trees around the player and takes away the ones left behind, so there is woodland wherever they walk: `bind(forest_generator, osm_index)` then `update($ProtoController.position)` every frame, the same shape as `OsmGroundData`. `RADIUS` (200 m) is where woodland appears and disappears. `_repack()` (which cells are in range) is throttled by `REBUILD_MOVE` (50 m), but `_work()` (bake, then grow) deliberately is **not** — a cell cannot be grown until its tree meshes exist, so it has to be able to finish while the player stands still.
- **The streaming unit is a `CELL`, not a forest**, and that is the fix for stands not appearing until you are inside them: the biggest here is 31 ha, so planting per stand meant nothing until its far edge came within range and then the whole thing arrived at once, including the parts hundreds of metres away that were already on screen. A cell is planted when it comes within RADIUS and dropped when it leaves, so a stand builds up as you walk into it (measured: 12 → 22 → 33 → 45 trees as you approach, then 0 as you leave). It also culls better than a stand-sized node would, since each cell's MultiMeshes have a 32 m AABB.
- **`CELL` is bound by the tree density, not by culling**, which is the opposite of what it looks like: a cell gets `density * cell_area` trees, so it must be big enough to hold one. At 0.001/m^2 a 16 m cell gets `floori(0.256)` = **0 trees and the forest silently disappears**; 32 m gets exactly 1. That is why CELL is 32 and not smaller, and it is why raising the density is not the way to finer streaming either (0.004/m^2 would put ~490 trees inside RADIUS, ~7x the vertex load).
- **A cell's trees are seeded from its key and the feature's way id**, so a tree never moves because a neighbour streamed in or out. Trees are placed by trying to fill the cell to the density and letting the outline reject the ones outside it, so a cell the forest only clips the corner of gets fewer trees rather than a full cell's worth pushed against the edge.
- **`ForestGen.recycle()` pools the MultiMeshInstance3Ds**, and the reason is node count rather than CPU. Measured at CELL 32: ~148 cells in range, node count rises to 45 entering woodland and then **stays at 45** while the trees drop to 0, the pool draining 45 → 18 as the next stand is planted. What pooling does *not* save is the real work — sampling positions and raycasting the ground is ~100 us a cell and happens either way — and the node count is far too low for it to show in a frame time. Do not expect a number here.
- `ForestGen.plant_forest_in_rect(type, points, rect, seed)` takes the area's **outline** (`PackedVector2Array` in world XZ, closing vertex included), not a bounding box: the tree count comes from `polygon_area(points)` and the positions from rejection sampling in the polygon's box. Godot 4 dropped `Geometry2D.compute_polygon_area()`, so the area is a hand-rolled shoelace sum. In a world of metres that really is square metres now, so the densities in `_plan` mean what they say (0.001/m² of oak is one tree every ~32 m). `rect` is the streaming cell, so a cell grows only the part of an outline that falls inside it, and `seed` is what makes that repeatable. It returns the `MultiMeshInstance3D`s it added rather than keeping them, which is what lets the streamer take them away again — it only ever removes what it planted. `MAX_PLACEMENT_TRIES` (32) bounds the sampling; the worst fill ratio over the 1366 forests here is 0.08, so it is never hit in practice, and a tree with no spot is left out rather than piled on the origin.
- **The tree meshes are the frame budget, and they were authored as hero trees.** Leaves are 82% of an oak's 107 691 vertices and 94% of a spruce's 299 377, so one stand at the old 0.01/m² was **~78 M vertices a frame** — which is what made the game hang rather than run slowly, and it looks like "no trees" because the first frame carrying them never presents. `bake_next()` applies a forest LOD (`_apply_lod`: `bark_rings` 8→4, leaf counts ×`LOD_LEAF_DENSITY`) before `regenerate()`, which brings a tree to ~27k and a stand to **1.87 M/frame, a 42x cut**, and makes the bake 4-6x faster as a bonus. `TreeGenPresets` is used by nothing else, so this costs no other feature; the constants live in `ForestGen` rather than in the presets so the hero tree stays available. The other half of the fix was the density (0.01 → 0.001/m²), which is both 10x cheaper and a believable woodland. Measured at 1280×720 on llvmpipe: 58 ms without the forest, 133 ms with, bounded over a 360 m walk (worst 148 ms) — the trees cost ~74 ms and are the next thing to turn down if it is still slow.
- Baking one tree is 30-370 ms of procedural geometry, so it is **one mesh per `bake_next()` call**, on a frame budget shared with planting. Three things make that budget behave, and each was wrong first:
  - **Planting is not gated on the budget.** One bake is 30-60 ms against a 6 ms budget, so a bake always spends the whole thing, and gating planting on it meant nothing was ever grown while anything was left to bake: the first stand took 21 frames to appear. Planting now stops on the budget only when a *second* stand is waiting.
  - **`bake_next()` round-robins species** via `_cursor`, not "the first species with room left". Taking the first one bakes all ten oak variants before any spruce, and a stand holding one spruce then waits for all of them.
  - **A species is asked for `min(VARIANTS, its tree count)` meshes** (`_wanted_count`). Spruce is a tenth of one percent of an oak stand, so asking for ten spruce meshes for the one spruce in it is nine bakes of nothing.
- **Mesh diversity is free; the number of meshes is not the cost.** 240 trees drawn as 3 distinct meshes x 80 instances measured 135.9 ms and as 24 distinct x 10 measured 134.2 ms — the same, because what a frame pays for is instances x vertices-per-tree and splitting instances over more meshes changes neither. So `VARIANTS` is nearly free (bake time and memory only, ~30 ms and ~0.9 MB each) and a stand is split across the variants rather than picking one mesh for all its trees: 71 trees over 11 distinct meshes costs 131.5 ms at 36 draws, against 133.8 ms at 16 draws for the same 71 trees on 2 meshes. **A pool of 100 unique trees would therefore buy no frame time at all** while costing ~3 s of baking and ~86 MB.
- **A stand waits for its whole variant set, not just the first mesh.** Otherwise it is planted two frames in, when one variant exists, and every tree in the stand the player is standing in is that one mesh — which makes `VARIANTS` pointless. The wait costs no real time, since the baking happens either way.

## Gotchas

- GDScript uses tabs; the asset-pipeline Python uses 4-space indent. `.gd.uid` and `.import` files are committed (Godot's UID system) — keep them when renaming/duplicating scripts, and regenerate with `--headless --import`.
- **The headless renderer never parses a shader.** `--headless` (and `--headless --rendering-driver vulkan`) still ends up on `RendererDummy`, where `Shader.set_code` is a no-op: even deliberately broken shader code reports nothing. So a clean headless smoke run says nothing about `ground.gdshader`; to compile it, run windowed (a ~3 s window on `DISPLAY=:0`) and look for `Vulkan … Using Device`, plus any `Shader compilation failed`. Two shader-language rules that shape the file: a function may only be used from a function **below** it, and a uniform array's size has to be a **literal** (a `const` identifier is not constant-folded there — godotengine/godot#72087), so the loop bounds are literals too and `OsmGroundData.MAX_LINES`/`MAX_AREA_EDGES` have to be kept in step by hand.
- There's no display feedback in this environment, so verify the ground visually by rendering and then reading the image back: `--resolution` plus a frame counter that saves `get_viewport().get_texture().get_image().save_png(...)`, then probe the PNG for the feature colours. Flat debug uniforms (magenta road, yellow building, cyan water, red rail, black ground) plus a white `AMBIENT_SOURCE_COLOR`/`TONE_MAPPER_LINEAR` environment make that unambiguous — with the scene's own sky-only ambient (there is **no** `DirectionalLight3D`) a colour probe on the real albedo is unreliable. Aim the `Camera3D` directly: the brackeys controller owns its yaw/pitch and overwrites `ProtoController.rotation`.
- `scripts/osmdataset/` is the real package; `scripts/osm_dataset/` (with the underscore) is an empty leftover directory — don't add files there. `osm_to_json.py`'s docstring still names the old one.
- `Image.load_from_file` (rather than loading a Resource) makes Godot warn "this will not work on export" — expected in this demo, not a bug to fix.
- Trees are placed by raycasting the terrain (`ForestGen._ground_height_at`, reusing one `PhysicsRayQueryParameters3D`), so anything that changes height normalization or the heightmap's scale/centering makes forests float or sink. That raycast only hits terrain inside the streamed `LOAD_RADIUS`, so anything placed by raycast has to be near the focus point. Note it hits *anything* in the way: a ray straight down from the spawn hits the player's own capsule top at y=5.977, well above the 4.236 m of terrain under it.
- **`MultiMesh` instance data is a no-op under `--headless`.** `set_instance_transform()` silently does nothing and `get_instance_transform()` reads back identity, even for a bare MultiMesh with a BoxMesh in and out of the tree — the dummy renderer never allocates the buffer. So a headless probe will tell you every tree is at the origin, `get_aabb()` is empty and nothing is visible, and none of that is real. Verify tree placement by rendering (with/without the forest, then difference the images); only `instance_count` and the mesh's own vertex counts can be trusted headless.
- Startup cost: ~0.5 s per generated forest (100 forests ≈ 56 s). Lower the loop cap in `main.gd` when iterating on placement. Indexing all 14410 features into `OsmQuadtree` costs ~0.35 s and runs in `main.gd` before the forest loop.
- Free-fly toggle is the `freefly` action in `project.godot`, bound to physical keycode 59 (the `Ö` key on a Swedish layout), not a letter. Remap via the Input Map tab.
